# 开发规范

## 1. 开始修改前

1. 阅读根目录 `AGENTS.md`、`README.md`（存在时）、与任务直接相关的 `.codex/*.md`、`docs/requirements/README.md`（存在时）以及相关源码。
2. 搜索已有需求目录，按产品能力判断本次请求属于已有需求还是新的独立用户目标。
3. 执行 `git status -sb`，保留并避开用户已有的无关修改，不得擅自清理工作区。
4. 修复缺陷或性能问题时，优先添加能够稳定复现问题的回归测试，再修改实现；无法合理自动化测试时记录原因和替代验证方式。
5. 不要修改或提交 `node_modules/`、`.next/`、`out/`、`dist/`、coverage、临时缓存等可重新生成的构建产物，除非仓库规则明确要求。

## 2. 编码原则

1. **先数据模型，后页面。** 新增 Components 和 Templates 优先通过数据驱动，不复制页面硬编码内容。
2. **优先复用。** 重复出现的 UI 结构应评估抽取组件，但不要为了“可能复用”提前过度抽象。
3. **shadcn/ui 优先。** 通用 UI 不重复造轮子。
4. **Motion 只服务体验。** 动画必须有明确的视觉或交互价值，避免影响性能和可访问性。
5. **静态部署优先。** 引入服务端能力前必须确认 Static Export 无法满足需求，并更新技术方案档案。
6. **响应式是完成标准。** 桌面端和移动端都必须可用。
7. **图片资源必须优化。** 控制尺寸、格式、加载策略和 Gallery 首屏资源量。
8. **避免过度工程化。** V1 不主动引入数据库、登录、支付、CMS。
9. **保持内容可迁移。** 内容 Schema 不与具体 UI 实现强绑定。
10. **商业转化保持简单。** Templates 展示参考报价和联系方式，通过人工沟通成交。

## 3. 验证要求

修改完成后根据影响范围执行最低必要验证：

- TypeScript / ESLint 等静态检查（项目配置存在时）；
- 相关单元、组件或回归测试；
- `pnpm build`，涉及 Static Export 时必须确认 `out/` 能正常生成；
- PWA 变更检查 manifest、Service Worker 和安装相关配置；
- Motion / UI 变更至少验证桌面端和移动端布局；
- 数据 Schema 变更验证生成脚本及已有数据兼容性；
- 部署变更验证 GitHub Actions 和又拍云同步逻辑。

不能执行某项验证时，必须在实现记录和最终回复中明确说明，不能写成“已通过”。

## 4. 完成原则

代码完成、测试通过、构建成功、提交远程和发布上线是不同状态，必须分别如实描述。

涉及产品行为、架构、发布方式或项目规则的修改，还必须完成对应需求档案更新，文档闭环属于完成标准的一部分。
