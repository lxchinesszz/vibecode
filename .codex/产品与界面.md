# 产品与界面规则

## 1. 产品定位

VibeCode 的商业模型必须始终围绕以下链路设计：

```text
免费 Components 获取精准流量
        ↓
真实效果 / Demo / Prompt 建立信任
        ↓
Related Templates 承接需求
        ↓
完整 Template 展示产品能力
        ↓
技术方案 + 参考报价
        ↓
微信 / Email 人工沟通成交
```

核心原则：

> **组件是免费引流产品，模板是收费核心产品。**

Components 与 Templates 不是两个平均分配资源的内容频道。组件可以大量生产，用于 SEO、搜索、分享和能力展示；模板数量可以更少，但必须是高完成度、可演示、可交付的精品产品。

## 2. 前台分类原则

### 2.1 使用用户语言，而不是开发者语言

网站面向一般用户时，前台信息架构优先回答：

- 我想做什么？
- 我需要哪个页面或功能？
- 我想做哪一类网站或产品？

不要要求用户先理解 Business Component、Static Export、Full Stack、PWA、Next.js 等工程概念。

统一原则：

> **前台分类使用用户语言；技术语言用于标签、筛选、实现说明和交付方案。**

### 2.2 分类层级

内容分类最多保持三层认知：

```text
一级：用户目标
二级：具体场景
三级：Tags / 筛选条件
```

不要为了 SEO 无限增加目录层级。技术栈原则上作为 Tag 或 Filter，而不是主要商业分类。

---

## 3. Components：免费流量产品

### 3.1 组件目标

Component 的首要职责不是直接收费，而是：

1. 获取搜索和长尾 SEO 流量；
2. 通过真实效果吸引点击和传播；
3. 免费提供可直接使用的 Prompt；
4. 展示实现能力并建立信任；
5. 把有完整产品需求的用户导向 Related Templates。

不做 Button、Input、Select 等价值较低的基础原子组件，优先收录用户能够直接理解和搜索的完整页面区块、业务能力和交互效果。

### 3.2 组件主分类

组件按“我要做哪个部分”进行分类，初始分类建议：

| 分类 | 典型内容 |
| --- | --- |
| 导航 | Navbar、Sidebar、Tab Bar、Mega Menu、Mobile Menu |
| 首屏 | Hero、产品首屏、SaaS Hero、App Hero |
| 登录注册 | Login、Register、OTP、Social Login、Forgot Password |
| 价格 | Pricing Table、Pricing Cards、套餐对比 |
| 功能展示 | Features、Bento Grid、Feature Showcase |
| 数据展示 | Dashboard、Stats、Charts、KPI |
| 表单 | Contact、Checkout、Profile、Settings |
| 搜索筛选 | Search、Filter、Command Palette |
| AI | AI Chat、Prompt Input、Thinking、Tool Call |
| 上传 | File Upload、Image Upload、Drag & Drop |
| 内容 | Blog List、Article、FAQ、Timeline |
| 社会证明 | Testimonials、Logo Wall、Reviews |
| CTA | Newsletter、Download、Contact、Purchase |
| 页脚 | Footer |
| 动效 | Scroll Reveal、Parallax、Card Stack、Transition、数字滚动等 |

分类可以随真实内容增长调整，不要求 V1 一次性填满。

### 3.3 Tags 与筛选

一个 Component 只有一个主要分类，但可以拥有多个标签，例如：

```text
分类：首屏

Tags:
SaaS
AI
Dark
Gradient
Motion
Next.js
Responsive
```

技术栈、视觉风格、行业、交互方式都优先作为 Tag / Filter。

### 3.4 Component 详情页

每个组件至少包含：

- 大尺寸效果预览；
- 在线 Demo（适合时）；
- 功能 / 交互说明；
- 完整 Prompt；
- Copy Prompt；
- 技术栈；
- Tags；
- Related Templates。

组件内容永久免费。

Related Templates 是组件详情页的核心商业转化区域，不应只作为普通“相关推荐”弱化处理。

---

## 4. Templates：收费核心产品

### 4.1 模板目标

Template 是已经完成、能够演示并可以作为完整产品交付的项目。

用户进入 Template 页面后，产品目标从“获取免费 Prompt”切换为：

> **让用户判断这个成品是否适合自己的需求，以及需要哪种交付方案。**

Template 不应该只是 Component 的“大号版本”，而应该按照商品详情页的逻辑展示。

### 4.2 模板按商业用途分类

Template 主分类按“我要做什么网站 / 生意”设计，而不是按技术栈设计。

初始分类建议：

| 分类 | 用户需求 |
| --- | --- |
| 企业官网 | 公司介绍、品牌展示、业务获客 |
| 外贸官网 | 海外获客、多语言、询盘 |
| 海外销售 | 产品销售、Landing、独立站 |
| SaaS | 软件产品、订阅服务 |
| AI 产品 | AI Chat、AI 工具、AI SaaS |
| 工具网站 | Calculator、Converter、Generator 等 |
| App / PWA | 移动 Web App、轻量应用 |
| 博客 / 内容 | Blog、Docs、知识库 |
| 个人网站 | Portfolio、Resume、个人品牌 |
| Landing Page | 广告投放、产品发布、活动页 |

### 4.3 模板二级场景

一级分类下可以继续按真实业务场景细分。

例如企业官网：

```text
企业官网
├── 科技公司
├── 软件公司
├── 制造业
├── 外贸公司
├── 咨询公司
├── 教育培训
├── 餐饮
└── 工作室
```

海外销售：

```text
海外销售
├── 独立站
├── 单品销售
├── App Landing
├── SaaS Landing
├── 数字产品
├── 课程
└── 品牌官网
```

二级分类只在内容数量足够时建立，不提前制造空分类。

### 4.4 Template 详情页

每个模板至少展示：

- 完整效果图；
- Live Demo；
- 页面列表；
- 功能列表；
- 产品适用场景；
- 技术栈；
- Built with Components；
- 多种交付技术路线；
- 各路线能力边界；
- 参考报价；
- 微信 / Email 联系方式。

不做在线支付、购物车和订单系统。

---

## 5. 模板交付路线

Static / Full Stack / Admin 不作为 Template 的主要前台分类，而是在用户进入模板详情页后用于选择交付方案。

### Static / 纯静态

适合企业展示站、Landing Page、工具站、无账号体系的小型 PWA。典型能力包括 React / Next.js Static Export、LocalStorage / IndexedDB、PWA 和静态托管。

### Full Stack / 全栈

适合账号体系、云端数据、API、多端同步。可采用 Next.js、PostgreSQL、Auth、独立后端或 Serverless。

### Admin / 后台管理

面向正式运营产品，可包含用户管理、内容管理、数据管理、Dashboard、RBAC 和操作日志。

同一个 Template 可以提供多套技术方案。模板详情页必须说明能力边界、适用场景和参考报价差异，不使用含糊的“基础版 / 高级版”代替技术边界。

---

## 6. Components 与 Templates 的商业闭环

两类内容必须支持双向关联：

```text
Component → Used in Templates
Template  → Built with Components
```

更重要的是建立可持续的内容生产方式：

```text
开发一个完整收费 Template
        ↓
拆解出多个可独立使用的 Component
        ↓
为每个 Component 提供效果 + Demo + Prompt
        ↓
形成多个免费 SEO / 分享入口
        ↓
每个 Component 反向导流原 Template
```

例如：

```text
Travel Budget Template
├── Budget Dashboard
├── Expense Form
├── Statistics Chart
├── History List
├── Settings Page
├── Bottom Sheet
├── Number Animation
├── Progress Ring
├── Swipe Action
└── Tab Navigation
```

因此不追求 Components 与 Templates 数量对等。长期可以形成“数百个免费组件 + 少量精品收费模板”的结构。

## 7. URL 与搜索结构

URL 应直接体现用户能够理解的分类：

```text
/components
/components/hero
/components/login
/components/pricing
/components/navigation

/templates
/templates/corporate
/templates/corporate/manufacturing
/templates/corporate/software

/templates/overseas
/templates/overseas/saas
/templates/overseas/product
```

未来可以围绕分类、场景和标签形成更精准的内容入口，例如：

- AI SaaS 首屏组件；
- 外贸网站导航组件；
- SaaS Pricing 组件；
- 制造业官网首屏；
- AI 产品登录页；
- 海外产品 Landing Page。

避免为了关键词机械生成无真实内容的页面。

---

## 8. 首页信息架构原则

首页不是传统 SaaS 营销页，也不应该平均展示 Components 与 Templates。

首页承担两步任务：

```text
第一步：通过大量高质量免费 Components 吸引浏览
第二步：在浏览过程中自然把完整需求导向 Templates
```

建议导航保持简单：

```text
VibeCode

组件    模板    定制    搜索
```

“组件”菜单展示用户熟悉的功能分类，例如导航、首屏、登录注册、价格、AI、动效等。

“模板”菜单展示商业用途，例如企业官网、外贸官网、海外销售、SaaS、AI 产品、工具网站等。

首页内容优先级：

```text
简洁 Hero
↓
热门 / 最新 Components
↓
按组件场景继续发现
↓
穿插完整 Template
↓
更多 Components
↓
精选 Templates
↓
交付方案说明
↓
微信 / Email CTA
```

首页作品优先，减少无意义营销文案和大面积空洞 Hero。

---

## 9. UI 方向

默认采用黑色 / 深灰视觉体系：

- 大面积深色负空间；
- 卡片式 Gallery；
- 轻量渐变和高光；
- 大预览图、小面积品牌色；
- 强调真实作品截图和 Demo；
- 减少无意义装饰；
- 桌面端优先展示，同时保证移动端完整可用。

UI 设计必须服务于“浏览组件 → 发现模板 → 联系成交”的转化链路，而不是为了呈现 Developer Tool 风格本身。

---

## 10. 页面规划

- `/`：组件发现为主，穿插精选 Templates 和商业转化入口。
- `/components`：免费组件 Gallery，支持分类、标签、搜索和筛选。
- `/components/[slug]`：Preview、Demo、Prompt、Copy Prompt、Stack、Tags、Related Templates。
- `/templates`：按商业用途浏览完整模板。
- `/templates/[slug]`：效果、Demo、页面、功能、适用场景、Built with Components、交付路线、参考报价、联系 CTA。
- `/pricing`：技术路线和报价说明，不是购买套餐页。
- `/contact`：微信二维码、微信号（如需要）、Email、可承接范围。

---

## 11. V1 明确不做

- 用户注册 / 登录；
- 收藏云同步；
- 在线支付；
- 订单系统；
- CMS；
- 评论系统；
- 用户投稿；
- 实时数据库驱动页面。
