# 需求管理规则

所有会改变产品行为、架构、发布方式或项目规则的请求，都必须维护在 `docs/requirements/`。

## 1. 需求归属判断

- 按“产品能力归属”判断是否重复，不按用户本次措辞判断。
- 同一功能的增强、修复、性能优化、交互调整、验收变化和边界补充，都归入原需求目录。
- 只有引入独立用户目标或新的产品能力时，才创建新需求目录。
- 无法可靠判断时，先说明准备归入哪个需求及理由，再请用户确认。
- 已创建的需求编号和目录不得因后续改名而改变。

## 2. 目录和编号

新需求目录格式：

```text
docs/requirements/REQ-YYYYMMDD-NNN-short-name/
```

规则：

- 日期使用需求首次提出日期；
- `NNN` 为当天从 `001` 开始的三位序号；
- 新目录必须从 `docs/requirements/_template/` 复制；
- 至少维护 `requirement.md`、`solution.md`、`implementation.md`、`changes.md`。

如果模板尚未建立，应先补齐 `_template/`，再创建首个正式需求。

## 3. 已有需求的后续改动

重复或延续需求不得新建目录，必须：

1. 在原目录 `changes.md` 按时间追加记录，保留用户请求、归属判断、处理结果和验证结果。
2. 产品目标、范围或验收标准变化时更新 `requirement.md`。
3. 技术方案、数据结构或关键取舍变化时更新 `solution.md`，保留决策原因。
4. 实际代码、测试、构建或发布状态变化时更新 `implementation.md`。
5. 在 `docs/requirements/README.md` 的“变动时间线”最上方增加记录。

## 4. 变动点引用

- 总时间线中的每条变动必须链接到该需求 `changes.md` 中本次变动的具体标题锚点，不能只链接需求目录。
- `changes.md` 每条记录使用唯一、可读的二级标题，例如 `## 2026-09-17 调整首页组件分类`。
- 一次请求涉及多个已有需求时，分别记录，并在总时间线分别引用。
- 时间线按事件时间倒序排列；同一个需求可以出现多次。
- 代码提交、产物或发布地址存在时，记录在对应变动条目或实现文档中。

## 5. 状态与完成门禁

统一状态：

```text
待分析 → 待确认 → 已确认 → 开发中 → 待发布 → 已发布
```

允许额外状态：`已阻塞`、`已取消`。

规则：

- 用户明确要求实现时，可以从“已确认”直接进入开发，但仍须先建立或更新需求档案。
- 代码完成、测试通过、构建成功、已提交、已发布必须分别如实记录。
- 未实际推送远程或未提供可访问产物，不得写成“已发布”。
- 完成代码工作时，需求文档闭环属于完成标准，不得留到以后补写。

## 6. 文档职责

- `requirement.md`：为什么做、用户目标、范围、非范围、验收标准。
- `solution.md`：怎么做、架构、数据结构、关键取舍和原因。
- `implementation.md`：当前实现、代码位置、测试、构建、提交和发布状态。
- `changes.md`：每一次需求变化和处理记录，只追加历史，不覆盖旧记录。
- `docs/requirements/README.md`：需求索引和跨需求总时间线。
